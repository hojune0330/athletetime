# 기록 모음·소속 통계 의사결정표

## 목적

선수 기록을 찾고 모아 보는 흐름은 바로 개선하되, 개인정보·동명이인·운영 책임을 바꾸는 기능은 작은 UI 수정처럼 섞어 출시하지 않는다. 이 문서는 여러 사용자 관점 검토에서 나온 결론과, 사장님 결정이 필요한 다음 선택을 분리한다.

## 이미 적용한 안전한 기준

| 화면 | 지금의 기준 | 지키는 이유 |
| --- | --- | --- |
| 기록 검색 | 이름과 소속으로 찾은 결과를 `선수 후보`로 표시 | 이름이나 소속이 같다고 같은 사람으로 단정하지 않는다. |
| 기록 모음 | 사용자가 고른 선수 후보만 최대 6명까지 함께 본다 | 선택은 되돌릴 수 있고, 원본 공개 기록은 바뀌지 않는다. |
| 모음 상세 | 후보별 이름·소속을 기록 행마다 함께 표시 | 서로 다른 사람의 기록이 한 사람의 이력처럼 보이지 않게 한다. |
| 소속 통계 | 소속 명단이 아닌 공개 기록의 집계만 제공 | 팀 화면이 개인 프로필이나 개인 보관함의 우회 경로가 되지 않게 한다. |
| 소속 지표 | 출전이 확인된 대회, 확인한 입상, 기록 개선 확인, 확인한 기록 | 공식 명단·공식 메달·완전한 이력을 뜻하지 않는다. |

## 지금 결정하지 않고 남겨 둔 항목

### 1. 기록 모음의 인원 한도

현재 한 모음은 선수 후보 6명까지다. 이 한도는 작은 화면에서 이름·소속·기록을 섞지 않기 위한 UX 안전선이다.

사장님 결정이 필요한 선택:

| 선택 | 결과 |
| --- | --- |
| 6명 유지 | 비교와 검토가 빠르고, 학생 사용자의 화면 피로가 가장 낮다. |
| 12명으로 확대 | 소규모 훈련 그룹에는 편하지만, 모음의 정리·수정 화면을 다시 설계해야 한다. |
| 팀 단위 선택을 별도 기능으로 제공 | 많은 선수를 담는 목적에는 맞지만, 기록 모음과 완전히 다른 `소속 통계` 제품으로 유지해야 한다. |

권장: 팀 전체를 개인 기록 모음에 넣지 않고, 현재의 소속 통계 화면을 팀 성과판으로 발전시킨다.

### 2. 계정에 기록 모음을 저장하는 기능

브라우저 안의 기록 모음을 계정에 동기화하기 전에, 공개 기록의 현재 ID와 별도로 변하지 않는 `record_uid`와 `subject_uid`를 정해야 한다. 데이터 정정이나 동명이인 분리 뒤에도 사용자가 숨긴 기록·모음이 다른 기록에 옮겨 붙지 않게 하기 위함이다.

결정 전에는 다음을 출시하지 않는다.

- 자동 계정 이관
- 여러 기기 동기화
- 내 기록이라는 본인 확인 표현
- 계정과 공개 선수 기록의 자동 연결

### 3. 소수 인원 소속 통계

중·고·초등 소속의 `시즌 × 종목 × 부문`처럼 작은 그룹은 한 건의 입상이나 최고 기록만으로 특정 선수를 짐작하게 할 수 있다. 서버가 그룹의 고유 선수 수를 기준으로 세부 수치를 숨기는 기준이 필요하다.

권장 초안: 고유 선수 5명 미만의 교차 집계는 `자료가 적어 세부 수치를 보여주지 않아요`로 통합한다. 전체 소속의 인원이 5명 미만일 때도 인원 숫자 대신 `5명 미만`만 표시한다.

이 수치는 공개 범위와 운영 원칙을 함께 정해야 하므로, 사장님 승인 전에는 구현하지 않는다.

### 4. 개인 메모와 사진

개인 메모는 공개 기록·검색·소속 통계와 완전히 분리된 계정 전용 보관함이어야 한다. 현재 공개 이미지 업로드 경로는 개인 사진에 재사용하지 않는다.

결정 전 조건:

- 모음·메모·사진은 다른 계정이 ID를 알아도 내용이나 존재 여부를 알 수 없게 한다.
- 운영자 화면에는 메모 본문·사진·다운로드 주소를 넣지 않는다.
- 삭제·내보내기·비밀번호 재설정 뒤에는 최근 재인증과 전체 세션 종료를 정한다.
- 사진은 공개 이미지 저장소와 별도의 비공개 저장소, 짧은 열람 주소, 파일 메타데이터 제거 기준을 정한다.

권장 출시 순서: 계정 기록 모음 → 텍스트 메모 → 제한된 사진 베타. 사진은 텍스트 메모와 한 번에 열지 않는다.

### 5. 오픈 채팅

현재 공개 채팅은 인증된 회원 채팅으로 바꾸기 전까지 확장하지 않는다. 브라우저가 보내는 사용자 식별자나 신고자 값을 신뢰하면 별칭 변경·신고 조작·차단 우회가 가능하기 때문이다.

다시 검토하는 최소 조건:

- 서버가 발급한 짧은 수명의 채팅 연결 티켓
- 이메일 인증 회원만 읽기와 쓰기를 허용하는 제한 베타
- 서버 측 신고 식별, 발신 제한, Origin 검사, 메시지 길이 제한
- 데이터베이스 장애 시 메모리 저장으로 성공한 것처럼 보이지 않게 처리
- 미성년 보호와 신고 대응 담당 체계

## 다음 구현 순서

1. 사장님이 위 다섯 항목의 우선순위와 정책 값을 결정한다.
2. 결정된 항목마다 데이터 계약·권한 테스트·오류 복구 화면을 먼저 만든다.
3. 소수 내부 계정 또는 제한 베타에서 운영 지표를 확인한다.
4. 통과 기준을 만족한 항목만 공개 화면에 연다.

이 순서를 지키면 기록 검색과 소속 통계의 현재 가치를 해치지 않으면서도, 민감한 기능을 나중에 되돌릴 수 없는 방식으로 서두르지 않게 된다.
