# 개인 보관함 출시 경계

## 목적

개인 메모와 사진은 공개 기록, 소속 통계, 커뮤니티와 분리된 계정 전용 보관함으로만 제공한다.
이 문서는 기능을 서두르지 않기 위한 출시 기준이다. 아직 보관함 API나 사진 업로드를 출시하지 않는다.

## 지금 확정하는 경계

1. 개인 보관함은 검색, 추천, 공유 카드, 소속 통계, 관리자 대시보드에 포함하지 않는다.
2. 기존 `/api/upload`와 Cloudinary 공개 URL 경로는 개인 메모 사진에 재사용하지 않는다.
3. 개인 보관함 API는 소유자가 아닌 요청에 대해 존재 여부를 알리지 않는 `404`만 반환한다.
4. 운영자 화면에는 개인 메모 본문, 사진, 다운로드 주소를 넣지 않는다.
5. 공개 기록과 계정 이메일을 자동으로 연결하거나 동명이인 기록을 자동 병합하지 않는다.
6. 채팅의 공개 확대와 개인 보관함 출시는 서로 의존하지 않는다.

## 소속 통계의 공개 경계

1. 소속 통계는 공개 결과를 집계한 화면이며, 선수 명단이나 개인 보관함의 우회 화면이 아니다.
2. 팀 검색과 상세 응답에는 이름, `athleteKey`, 원본 기록 배열, 소속 이력, 개인 메모, 첨부물을 넣지 않는다.
3. 팀에서 개인 기록을 보려면 빈 `기록 찾기` 화면에서 이름과 소속을 새로 입력한다. 팀 화면은 그 검색어와 개인 선택을 자동 전달하지 않는다.
4. `출전이 확인된 대회`, `모은 기록에서 확인한 입상`, `기록 개선 확인`은 공개 결과 범위에서 계산한 집계임을 고지한다.
5. 소속의 실제 재적 인원, 공식 명단, 공식 메달 집계, 팀 순위를 뜻하는 표현은 사용하지 않는다.

## 출시 순서

### 단계 A: 계정 기반 기록 모음

- 브라우저에 있던 기록 모음을 로그인 계정에 옮긴다.
- 성공한 이관에는 항목 수와 시간만 담은 영수증을 남기고, 원래 브라우저 자료를 즉시 지우지 않는다.
- 네트워크 실패, 중복 요청, 공유 기기 계정 전환을 계약 테스트로 막는다.
- 이 단계 전에는 `record.id`와 `athleteKey`를 계정 데이터의 영구 참조로 쓰지 않는다. 데이터 릴리스와 분리된 안정 참조 설계가 선행되어야 한다.

### 단계 B: 텍스트 개인 메모

- 로그인과 최근 재인증을 확인한 본인만 생성, 수정, 삭제, 내보내기를 할 수 있다.
- 기본 화면 문구는 `나만 볼 수 있는 개인 메모예요.`로 한정한다. 종단간 암호화나 운영자가 기술적으로 절대 볼 수 없다는 표현은 사용하지 않는다.
- 메모 원문과 제목은 일반 로그, 분석 이벤트, 오류 보고에 기록하지 않는다.
- 삭제와 복구 기간, 계정 삭제 시 처리, 백업 만료 방식은 출시 전에 실제 운영 설정과 함께 사용자에게 고지한다.

### 단계 C: 사진 제한 베타

- 전용 비공개 저장소와 전용 최소권한 자격 증명을 사용한다.
- 브라우저는 EXIF 위치 정보를 제거하고 허용된 형식과 크기로만 업로드한다.
- 서버가 소유권을 확인한 뒤 짧게 만료되는 읽기 주소를 발급한다. 공개 URL과 원본 파일명은 화면, 로그, 브라우저 저장소에 남기지 않는다.
- 사진 전체 ZIP 내보내기와 관리자 열람 UI는 제공하지 않는다.

### 단계 D: 오픈 채팅 재심사

- 이메일 인증 계정, 서버 발급 채팅 티켓, Origin 검증, 서버 기준 신고자 식별, 속도 제한, DB 저장 실패 시 쓰기 중단을 모두 갖춘 뒤에만 재검토한다.
- 제한 베타의 읽기와 쓰기 범위는 운영 담당자와 신고 처리 시간 측정 후 결정한다.

## 출시 차단 검증

- 다른 계정, 비회원, 관리자 계정이 보관함 ID나 첨부 ID를 알아도 개인 내용을 얻지 못한다.
- 비밀번호 재설정과 변경 후 기존 세션이 무효화되고, 보관함 열람·내보내기·영구 삭제는 재인증 전 막힌다.
- 이관 실패 시 기존 브라우저 모음이 보존되고, 성공 후 사용자가 직접 되돌릴 수 있다.
- 개인 메모와 사진은 팀 API, 기록 API, 검색 응답, 관리자 API에 포함되지 않는다.
- 미성년 사용자의 사진과 채팅 작성은 보호 절차가 확정되기 전까지 열지 않는다.

## 소유자 결정 대기

| 결정 | 선택지가 필요한 이유 |
|---|---|
| 안정 기록·선수 참조 설계 | 기존 `record.id`와 `athleteKey`는 데이터 정정 뒤에도 영구 참조를 보장하지 않는다. |
| 삭제 보관 기간 | 사용 편의와 민감 메모의 최소 보관 원칙 사이의 선택이 필요하다. |
| 미성년 보호 절차 | 14세 미만의 사진·채팅 기능을 열기 위한 보호자 동의 및 운영 방법이 필요하다. |
| 사진 저장소와 키 관리 | 비공개 객체 저장소, 짧은 만료 URL, 키 보관과 장애 복구 책임을 정해야 한다. |
| 예외 접근 절차 | 첫 출시에서는 제공하지 않으며, 필요성이 생기면 별도 2인 승인·감사·통지 설계가 필요하다. |
| 채팅 공개 범위 | 읽기 공개 여부와 베타 참여 조건은 실제 운영 역량에 맞춰 다시 결정한다. |
| 소수집단 표시 기준 | 학생 팀의 시즌·종목별 작은 집계는 개인을 추정하게 할 수 있으므로, 최소 표시 인원과 숨김 규칙을 정해야 한다. |
